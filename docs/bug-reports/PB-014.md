# PB-014. Перевод на сумму точнее цента принимается и делает оба счёта нечитаемыми

| Поле | Значение |
|---|---|
| Серьёзность | Critical — после одного запроса счета клиента не открываются ни через REST, ни через SOAP |
| Приоритет | High |
| Окружение | parasoft/parabank (digest `sha256:747453a0…`), http://localhost:8090/parabank · 11.10.2026 |
| Воспроизводимость | стабильно |
| Проверки | `collections/known-defects.postman_collection.json` → папка «Последним: портит счета»<br>`collections/transfer-boundaries.postman_collection.json` + `data/transfer-amounts.csv` → «три знака после запятой» |

## Шаги

1. Новый клиент, счета A и B.
2. `POST /services/bank/transfer?fromAccountId=<A>&toAccountId=<B>&amount=0.001`.
3. `GET /services/bank/accounts/<A>`.
4. SOAP `getAccount(accountId=B)`.
5. `GET /services/bank/customers/<id>/accounts`.

## Ожидаемый результат

Шаг 2 — 400: сумма с точностью больше цента не принимается. Если всё же принята — округляется, а счета остаются доступными.

## Фактический результат

Шаг 2 — `200 Successfully transferred $0.001 …`. Шаги 3–5: REST — `500` с HTML-страницей ошибки, SOAP — Fault `soap:Server` «Rounding necessary». Не открывается и список счетов клиента. Счета остаются нечитаемыми до сброса базы (`POST /services/bank/initializeDB`).

## Примечание

«Rounding necessary» — так `BigDecimal.setScale` сообщает, что значение нельзя привести к двум знакам без округления. Судя по этому, остаток записывается с тремя знаками, а при чтении приводится к двум. Отсюда и масштаб последствий: ломается не перевод, а каждое последующее чтение. В коллекции эти проверки стоят последними, а в наборе граничных значений у каждой итерации свой клиент — иначе один случай испортил бы остальные.
