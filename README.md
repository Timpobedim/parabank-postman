# parabank-postman — коллекции Postman для REST и SOAP демо-банка, Newman и mitmproxy

Пять коллекций Postman проверяют демонстрационный интернет-банк ParaBank через REST и через SOAP.
Newman прогоняет их по очереди и честно сообщает итог кодом возврата. mitmproxy нужен для двух задач:
пишет журнал обмена для баг-репортов и портит ответы банка, чтобы проверить сами проверки.
Найдено 7 новых дефектов, ещё 3 известных воспроизведены через SOAP.

**Стек:** Postman (коллекции v2.1) · Newman 6 · newman-reporter-htmlextra · Node.js · mitmproxy 12 ·
Python 3.12 · pytest · Docker · GitHub Actions · ruff · mypy (strict).

## Что внутри

| Коллекция | Что проверяет | Проверок |
|---|---|---|
| `parabank-rest` | клиент, счета, перевод, пополнение и снятие, история, поиск, кредит, ошибки; деньги сверяются до цента, JSON — по схемам | 70 |
| `parabank-soap` | те же операции по WSDL: разбор XML, SOAP Fault, тело не по схеме, DTD с внешней сущностью | 37 |
| `rest-vs-soap` | дифференциальная проверка: операция через один интерфейс видна через другой, данные совпадают поле в поле | 35 |
| `transfer-boundaries` | тест-дизайн суммы перевода: 12 классов эквивалентности и границ из `data/transfer-amounts.csv`, у каждой итерации свой клиент | 298 |
| `known-defects` | 14 дефектов: каждая проверка описывает ожидаемое поведение и падает, пока дефект есть | 62 |

Каждая коллекция сама регистрирует нового клиента через HTTP-форму: REST API ParaBank клиентов
не создаёт. Тесты поэтому не зависят ни от общих данных стенда, ни друг от друга.

```text
  known-defects: проверок 62, неожиданных падений 0, ошибок 0, известных дефектов 14 (PB-001, …, PB-020)
```

## Известные дефекты — как строгий xfail

Проверка с меткой `[PB-014]` в названии описывает **ожидаемое** поведение. Раннер считает её
падение ожидаемым и сборку не роняет. Если такая проверка **прошла**, то дефект исправлен или
проверка сломалась. В обоих случаях нужен человек, поэтому сборка краснеет («ИСПРАВЛЕНО?»).
Это тот же приём, что `xfail(strict=True)` в соседнем [parabank-ui-api](../parabank-ui-api).

Метка ставится на ту проверку, которую дефект действительно ломает. Например, перевод на ноль (PB-020)
не меняет остатки, поэтому в наборе граничных значений помечен только код ответа, а проверка
«остаток не изменился» остаётся обычной. Тест следит, чтобы у каждой метки был баг-репорт,
а у каждого баг-репорта — проверка.

| ID | Где | Дефект | Серьёзность |
|---|---|---|---|
| [PB-014](docs/bug-reports/PB-014.md) | REST, SOAP | **перевод на 0.001 принимается, после чего оба счёта не читаются ни через REST, ни через SOAP** | Critical |
| [PB-018](docs/bug-reports/PB-018.md) | REST, SOAP | пополнение и снятие на отрицательную сумму проходят | Major |
| [PB-015](docs/bug-reports/PB-015.md) | SOAP | перевод без суммы — `soap:Server` с текстом NullPointerException | Minor |
| [PB-016](docs/bug-reports/PB-016.md) | REST, SOAP | неизвестный тип счёта — 500 и «Index 7 out of bounds for length 3» | Minor |
| [PB-017](docs/bug-reports/PB-017.md) | SOAP | ошибки клиента (неверный пароль, нет счёта) приходят как `soap:Server` | Minor |
| [PB-019](docs/bug-reports/PB-019.md) | REST | нечисловая сумма — 404 с пустым телом вместо 400 | Minor |
| [PB-020](docs/bug-reports/PB-020.md) | REST, SOAP | перевод на ноль проходит | Trivial |
| [PB-001](docs/bug-reports/PB-001.md), [PB-002](docs/bug-reports/PB-002.md), [PB-003](docs/bug-reports/PB-003.md) | REST, **SOAP** | перевод больше остатка, на отрицательную сумму, на тот же счёт — воспроизводятся и через SOAP | Critical, Critical, Minor |

PB-014 найден на границе «точность суммы». Перевод на 0.001 проходит, а следующее чтение любого
из двух счетов падает: REST отдаёт 500 с HTML-страницей ошибки, SOAP — Fault «Rounding necessary».
Не открывается даже список счетов клиента. Так продолжается до сброса базы.
Поэтому в коллекции дефектов эти проверки стоят последними, а в наборе граничных значений у каждой
итерации свой клиент: иначе один случай испортил бы все остальные.

## Мутационная проверка через mitmproxy

Зелёный прогон ещё не значит, что проверки сильные. Ответ «200, всё хорошо» может пройти
и там, где банк ошибся на цент. Поэтому mitmproxy в режиме обратного прокси встаёт между Newman и банком
и портит ответ одним известным способом. Если ни одна проверка не упала, мутант выжил: такую
поломку настоящего банка коллекция тоже пропустит.

```text
$ uv run pbqa mutate
control                        чисто            падений 0   задето ответов 0    прокси без порчи
rest-balance-plus-cent         убита            падений 7   задето ответов 14   REST: остаток счёта на цент больше
rest-drop-account-type         убита            падений 9   задето ответов 14   REST: у счёта пропал тип
rest-flip-transaction-sign     убита            падений 2   задето ответов 3    REST: зачисление стало списанием
rest-other-customer            убита            падений 4   задето ответов 4    REST: в ответе чужое имя клиента
rest-empty-accounts            убита            падений 49  задето ответов 5    REST: список счетов пуст
rest-json-as-text              убита            падений 23  задето ответов 23   REST: JSON объявлен как text/plain
rest-transaction-date-zero     убита            падений 1   задето ответов 3    REST: дата операции — 1 января 1970
rest-transfer-500              убита            падений 2   задето ответов 2    REST: перевод отвечает 500
rest-transfer-wrong-amount     убита            падений 1   задето ответов 1    REST: в подтверждении перевода другая сумма
soap-balance-plus-cent         убита            падений 3   задето ответов 3    SOAP: остаток на цент больше
soap-drop-first-id             убита            падений 7   задето ответов 7    SOAP: пропал первый элемент id
soap-fault-server              убита            падений 3   задето ответов 3    SOAP: ошибка клиента выдана за ошибку сервера
soap-approved-false            убита            падений 1   задето ответов 1    SOAP: одобренный кредит стал отказом
slow-accounts                  убита            падений 10  задето ответов 10   ответ по счёту на 3,5 с медленнее

убито мутантов: 14 из 14
```

Сначала идёт контрольный прогон через тот же прокси без порчи. Он обязан быть зелёным, иначе
падения нельзя приписать мутациям. Если мутация не задела ни одного ответа, итог — «не применилась»,
а не «убита»: это ошибка каталога, а не заслуга коллекции.

**Двух мутантов коллекция сначала пропустила.** Первые 12 мутаций были убиты сразу. Тогда я
добавил две, которые, как я подозревал, пройдут, и обе выжили:
- **JSON с заголовком `text/plain`.** Postman разбирает тело и без правильного заголовка, а клиент
  на другом языке на таком ответе упадёт.
- **Дата операции, обнулённая в 1970-й год.** Дату не проверял никто.

После этого в коллекцию добавлены проверка заголовка у каждого JSON-ответа и проверка, что дата
операции — сегодняшняя. Обе мутации теперь убиты.

Мутации — чистые функции в `src/pbqa/mutations.py`, их проверяют тесты без прокси и сети.
Дополнение mitmproxy (`src/pbqa/addons/mutate.py`) — тонкая обёртка над ними.

## Журнал обмена для баг-репорта

```bash
uv run pbqa proxy --record flows.jsonl     # прокси :8091 → ParaBank :8090
node runner/run.js --feed feeds/full.json --base-url http://127.0.0.1:8091/parabank
```

В журнале на каждый обмен одна строка JSON: метод, адрес, код, время, типы и тела запроса
и ответа. По нему написаны баг-репорты этого проекта. Например, у PB-005 из журнала видно, что
без заголовка `Accept` текстовый ответ объявлен как `application/xml`.

Пароль в журнал не попадает. ParaBank передаёт его прямо в пути (`/login/{логин}/{пароль}`),
то есть в журналы любого веб-сервера и прокси на пути. Поэтому журнал маскирует путь, элемент
SOAP `<password>` и поля формы регистрации, и на это есть тест.

## Как запустить

```bash
docker compose up -d                          # свой ParaBank: http://localhost:8090/parabank
curl -X POST http://localhost:8090/parabank/services/bank/initializeDB   # создать базу в свежем контейнере
npm ci                                        # newman и htmlextra
uv sync --group dev                           # mitmproxy, линтер коллекций, тесты

node runner/run.js --feed feeds/full.json     # пять коллекций, ~20 с; отчёты — reports/*.html, *.xml
node runner/run.js --feed feeds/smoke.json    # только REST
uv run pbqa lint                              # линтер коллекций
uv run pbqa mutate                            # мутационный прогон, ~3 мин
uv run pbqa mutate --only rest-json-as-text   # одна мутация
uv run pytest                                 # раннер на заглушке, мутации, дополнения mitmproxy, линтер
```

Коллекции открываются в Postman через Import: `collections/*.json` и `environments/*.json`.

## Как проверялось

- **Коллекции** против своего контейнера ParaBank: 502 проверки, 0 неожиданных падений. Ожидаемые
  падения дают 14 известных дефектов: 6 из них видны и в наборе граничных значений. Прогон занимает
  около 20 с.
- **Мутационный прогон:** убито 14 мутантов из 14, контрольный прогон чистый.
- **pytest** — 47 тестов за 16 с:
  - раннер на заглушке сервера проверен на всех кодах возврата, на строгом учёте меток дефектов
    и на порядке прогонов;
  - каталог мутаций и маскирование паролей проверены без сети;
  - дополнения mitmproxy проверены на поддельных потоках (`mitmproxy.test`);
  - каждое правило линтера проверено, и проверено, что все коллекции проекта чистые;
  - метки дефектов и баг-репорты совпадают взаимно.
- `ruff`, `mypy --strict` — без замечаний.
- **Разведка до коллекций.** Одни и те же операции сначала были отправлены через REST и через SOAP
  скриптом, и ответы сравнены. Так нашлись PB-014…PB-020, а для PB-001…003 выяснилось, что SOAP
  ведёт себя так же.

### Что нашлось по ходу

- **В первой версии набора граничных значений все суммы, вычисляемые от остатка, уходили в запрос
  словом `BALANCE`.** Переменная данных итерации в Postman сильнее переменной коллекции, а имена
  совпадали. Раннер это заметил: проверка «весь остаток принят» получила 404. Теперь у вычисленной
  суммы своё имя, и причина записана комментарием в коллекции.
- **Метки дефектов сначала стояли на всех трёх проверках случая.** Раннер выдал 12 «ИСПРАВЛЕНО?»:
  например, у нечисловой суммы остаток действительно не меняется. Метки разнесены по колонкам
  `status_defect`, `balance_defect` и `read_defect`.
- **Линтер нашёл в моих коллекциях 9 запросов, где проверялся только код ответа.** Это служебные
  шаги вроде «открыть второй счёт». Теперь у каждого проверяется и содержимое.
- **В CI на свежем контейнере упали все коллекции.** У меня стенд уже был инициализирован, а в новом
  контейнере ParaBank схемы базы нет: регистрация отвечает 500 «bad SQL grammar [SELECT next_id FROM
  Sequence …]». Шаг CI теперь создаёт базу (`initializeDB`), как кнопка Initialize в админке, — он же
  в инструкции запуска.
- **Счётчик «задето ответов» сначала был нулевым у всех мутаций.** На Windows `terminate` убивает
  mitmdump без хука `done`, и итог не успевал записаться. Теперь он пишется при каждом изменении.

### Не проверялось

- **Charles Proxy не использовался.** Его задачи (перехват, подмена ответа, задержка, журнал)
  здесь решает mitmproxy, у которого есть скриптовый API для автоматизации. Опыт работы
  с интерфейсом Charles этот проект не подтверждает.
- **Приложение Postman.** Коллекции написаны в формате v2.1 и прогоняются Newman. Импорт в приложение
  Postman я не проверял.
- **MQ.** В WSDL ParaBank есть операции `startupJmsListener` и `shutdownJmsListener`, и вызов
  отвечает без ошибки. Но обмен через очередь не проверялся: куда слушатель подключается и что
  принимает, я не выяснял.
- **База данных ParaBank** (встроенная HSQLDB) напрямую не проверялась: только через REST и SOAP.
- **Мутации портят только ответы**, запросы не трогаются. Каталог из 14 мутаций не исчерпывает всех
  возможных поломок: «убиты все» значит лишь, что эти 14 коллекция замечает.
- **Публичный стенд** parabank.parasoft.com не использовался: у него общая база на всех.

```text
tests/         раннер на заглушке, мутации, дополнения, линтер и согласованность меток
```
